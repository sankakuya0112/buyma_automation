Agent 4: Monitor（在庫監視エージェント）
出品中の商品が仕入れ先でまだ買えるかを監視
次に実装

なぜ必要か：注文が入ったのに仕入れ先で売り切れていると、キャンセル→評価低下→アカウント停止のリスクがある。これを防ぐのが最優先。

Agent 2: Analyst（価格戦略エージェント）
BUYMA上の競合を分析して最適な出品価格を算出
Phase 3

なぜ必要か：現在は固定倍率（1.5〜1.8倍）で価格を決めているが、競合より高すぎると売れず、安すぎると利益が減る。動的な価格戦略が必要。

仕様
処理内容① BUYMAで同じブランド・カテゴリの商品を検索
② 競合の出品価格・出品数・販売実績を収集
③ 「競合最安値 − ¥1,000」or「利益率20%以上」のどちらかで最適価格を決定
④ 出品済み商品の価格も定期的に見直し
価格ルール競合0人（独占）→ 仕入れ×1.8倍
競合1〜3人 → 競合最安値−¥1,000〜3,000
競合4人以上 → 利益率15%以上なら出品、以下ならスキップ
出力outputs/reports/*_pricing_analysis.csv（改良版）
scripts/buyma_competitor_analysis.py ← 新規

2

↓
3

↓
4

↓

↓

6. 実装ロードマップ

Phase 1
完了
Lister エージェント（出品の自動化）
BaseBluスクレイピング → 利益計算 → BUYMA出品の全パイプライン。v4でプロショッパー仕様に到達。品番・説明文和訳・複数画像・買付メモ対応。
Phase 2
次にやること
Monitor エージェント（在庫監視）+ Scout 拡張
Monitor: 出品済み商品の在庫チェック。売り切れ検知→自動出品停止。これがないと注文キャンセルのリスクがある。
Scout: YOOX等の新しい仕入れ先を追加。共通スクレイパー基盤を構築。
Phase 3
利益の最大化
Analyst エージェント（競合分析・動的価格）
BUYMA内の競合出品を自動分析。固定倍率の価格戦略から、競合状況に応じた動的価格決定に移行。出品済み商品の価格を定期的に最適化。
Phase 4
運営の効率化
Support + Reporter エージェント
Support: 問い合わせの自動分類・回答ドラフト生成。対応速度UP→成約率UP。
Reporter: 月次の売上・利益レポート自動生成。どのブランド・カテゴリに注力すべきかを提案。

7. リスクと対策

高
アカウントBAN — BUYMAが自動操作を検知するとアカウント停止。
対策: ランダム待機（8〜15秒）/ headless=False / 人間的なマウス操作 / 1日の出品数を制限（推奨20件以下）
高
在庫切れキャンセル — 注文後に仕入れ先で売り切れ。キャンセル率上昇→ペナルティ。
対策: Monitor エージェントを Phase 2 で最優先実装。1日2回の在庫チェック。
中
為替変動 — 出品時と注文時で為替レートが大きく変動すると利益が圧縮。
対策: 為替マージンを5%以上確保。急激な円安時は出品価格を自動更新（Analystで対応）
中
仕入れ先のサイト変更 — BaseBlu等がAPI構造を変更するとスクレイピングが壊れる。
対策: エラーログ監視 / 複数の仕入れ先に分散（Scoutの価値）/ スクレイパーのモジュール化で修正を局所化
低
BUYMAのフォーム変更 — React要素のインデックスやclass名が変わるとフォーム操作が壊れる。
対策: インデックスベースではなくテキストベースの要素探索に移行（v4で一部対応済み）

8. Claude Code での使い方

各エージェントはClaude Codeのターミナルから個別に実行できます。将来的にはスケジューラーで自動実行も可能です。

やりたいことコマンド
全工程を一括実行python3 scripts/run_all.py
1件だけテストpython3 scripts/run_all.py --test
下書きのみpython3 scripts/run_all.py --draft
既存CSVで5件目からpython3 scripts/run_all.py --skip-scrape --from 5
ブランドID更新だけpython3 scripts/buyma_brand_lookup.py
在庫チェック（Phase 2）python3 scripts/stock_monitor.py
競合分析（Phase 3）python3 scripts/buyma_competitor_analysis.py
